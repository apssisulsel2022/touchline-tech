# TOUCHLINE ENTERPRISE ARCHITECTURE
## TAG-02 — Global Registry Foundation
### Artefact 04 — PostgreSQL Physical Data Model

> This document translates the approved logical data model into a PostgreSQL-oriented physical database architecture for the Global Registry Foundation. It is intentionally design-level and technology-aware, while remaining independent of application code, business workflows, and any specific UI implementation.

---

## 1. Design Objectives

The physical model is designed to satisfy the following enterprise goals:

- preserve a canonical registry identity model
- support strong governance and auditability
- enable high-volume identity lifecycle operations
- provide safe public lookup and QR resolution semantics
- support future child registry extension without weakening the core model
- remain compatible with PostgreSQL and with Supabase PostgreSQL hosting

This model assumes PostgreSQL as the primary relational database engine and uses standard PostgreSQL constructs such as UUIDs, checks, foreign keys, indexes, views, materialized views, JSONB, partitioning, and generated columns.

---

## 2. Core Design Principles

### 2.1 Schema Organization

A modular schema design is preferred to preserve ownership and reduce coupling.

Suggested schemas:

- registry_core: canonical identity, registry definitions, identifiers, authority, profiles
- registry_workflow: verification, duplicate, merge, import workflows
- registry_audit: provenance, change history, snapshots, status history
- registry_public: public-facing views and lookup-safe structures

### 2.2 Data Ownership

- registry_core owns canonical identity state
- registry_workflow owns case-based governance workflows
- registry_audit owns lineage, provenance, and historical evidence
- registry_public owns safe public presentation and resolution records

### 2.3 Storage Strategy

- Use normalized relational tables for core business concepts
- Use JSONB only for flexible metadata, policy payloads, and extensible attributes
- Use generated columns for search and display-safe values
- Use materialized views for query-heavy reporting and public lookups

---

## 3. Naming Convention

### 3.1 General Rules

- Use lowercase snake_case for all schema, table, column, index, and constraint names
- Use singular table names where the table represents a domain entity
- Use plural table names for collections only when the table is intentionally a set container; the preferred convention is singular entity names
- Use descriptive names that reflect business meaning rather than implementation mechanics

### 3.2 Recommended Naming Pattern

- tables: registry_identity, verification_case, merge_case
- columns: public_registry_id, verification_level_code, created_at
- foreign keys: registry_identity_id, canonical_identity_id
- indexes: idx_registry_identity_status, idx_verification_case_identity_status
- constraints: uq_registry_identity_public_id, ck_registry_identity_status

### 3.3 Status and Code Columns

- Use code-like suffixes for enumerated values: status_code, level_code, decision_code
- Use _at for timestamp columns
- Use _id for foreign keys
- Use _jsonb for JSONB payloads

---

## 4. PostgreSQL Features and Extensions

### 4.1 Required Core Features

- UUID data type
- CHECK constraints
- PRIMARY and FOREIGN keys
- UNIQUE constraints
- indexes
- views and materialized views
- JSONB
- partitioning

### 4.2 Recommended Extensions

- pgcrypto for UUID generation support
- pg_trgm for fuzzy matching and duplicate-search optimization
- unaccent where multilingual name normalization is needed

### 4.3 Supabase Compatibility

This design is compatible with Supabase PostgreSQL because it uses standard PostgreSQL features and does not depend on Supabase-only abstractions. The model can be deployed in a Supabase project with standard schemas, extensions, and migrations. It remains portable to any PostgreSQL-compatible environment.

---

## 5. UUID Strategy

### 5.1 Standard Strategy

All primary keys should use UUIDs rather than integers to support distributed identity semantics and external reference stability.

Recommended pattern:

- primary keys: UUID, generated by default using gen_random_uuid()
- foreign keys: UUID references to the owning entity
- business identifiers remain separate from internal UUIDs

### 5.2 Recommended Columns

Every major entity should include:

- id UUID PRIMARY KEY
- created_at timestamptz NOT NULL
- updated_at timestamptz NOT NULL
- deleted_at timestamptz NULL

### 5.3 UUID Governance

- internal id is the canonical system identity
- public_registry_id is the business-facing identifier and remains separate from the internal UUID
- alias identities and external references retain separate IDs

## 14. Performance Strategy

### 14.1 Core Performance Principles

- keep hot-path tables narrow and stable
- place composite indexes on common lookup combinations
- partition audit and history tables to reduce bloat
- use generated columns for search and display-safe values
- avoid overly wide rows in frequently updated tables

### 14.2 High-Value Query Patterns

| Query Pattern | Recommended Indexing |
| --- | --- |
| lookup identity by public ID | unique index on public_registry_id |
| list identities by registry definition and status | composite index on registry_definition_id, registry_status_code |
| fetch cases by identity and status | composite index on registry_identity_id, case_status_code |
| search identities by text | generated search_text column plus GIN or trigram support |
| fetch recent audit rows | partitioning plus time-based index |

### 14.3 Workload Guidance

- hot transactional tables should remain mostly row-store focused
- heavy reporting should use materialized views and asynchronous refresh
- public lookup tables should be optimized for read-heavy access patterns

---

## 15. Normalization Strategy

The model should follow strong normalization for the core domain and only use selective denormalization where it materially improves read performance.

### 15.1 Normalization Level

- 3NF is the baseline for canonical entities
- child entities such as attributes, evidence, history, provenance, and identifiers are separate tables
- status history and change records are stored as first-class records rather than as mutable flags

### 15.2 Selective Denormalization

The following may be denormalized into materialized views or cached summaries:

- active profile summary
- current verification state per identity
- duplicate case counts and aging metrics
- public profile availability and visibility state

This keeps the base tables normalized while offering efficient analytics views.

---

## 16. Migration Strategy

### 16.1 Migration Principles

- use versioned, additive migrations
- avoid destructive changes in the initial rollout
- create indexes and constraints in separate migration phases where performance requires it
- backfill historical data in batches
- preserve data lineage during migration

### 16.2 Recommended Migration Sequence

1. create schemas
2. create extensions such as pgcrypto and pg_trgm
3. create reference tables: registry_type, registry_definition, registry_authority
4. create core identity tables: registry_identity, registry_identifier, registry_identity_attribute
5. create workflow tables: verification_case, identity_claim, identity_evidence, duplicate_case, merge_case
6. create audit tables: registry_snapshot, registry_status_history, registry_change_record, provenance_record
7. create public-facing tables: public_profile, public_field_policy, qr_resolution_record
8. create import tables: import_batch, import_record
9. create indexes, constraints, and views
10. backfill and validate data

### 16.3 Compatibility During Evolution

- preserve old versions of policy JSONB during policy transitions
- keep historical status logic in audit tables rather than overwriting state
- support phased deployment of new registry types and policies

## 17. PostgreSQL Best Practices

### 17.1 Transaction and Integrity Practices

- use transactional updates for identity state changes and merge execution
- avoid partial updates to canonical state
- enforce invariants using constraints rather than application-side assumptions

### 17.2 Performance and Maintenance Practices

- monitor bloat on audit and history tables
- run periodic vacuum and analyze operations
- use connection pooling for high-throughput environments
- keep large JSONB payloads bounded and indexed where needed

### 17.3 Security Practices

- enforce least privilege for database roles
- isolate public-read surfaces through views rather than exposing raw tables
- use check constraints and strong foreign keys for data integrity
- avoid wide-open text fields for sensitive values without policy controls

### 17.4 Operational Practices

- keep schemas versioned and documented
- maintain migration rollback plans where practical
- treat audit tables as append-heavy and retention-managed

## 18. Relationship and Integrity Rules in Physical Form

### 18.1 Core Rules

- every registry_identity must reference a valid registry_definition
- every verification_case must reference one registry_identity
- every public_profile must reference one registry_identity
- every merge_case must reference one canonical_identity_id
- every merge_source must reference one merge_case and one registry_identity
- every evidence row must reference one verification_case
- every provenance row must reference a subject entity and its lineage context

### 18.2 Enforcement Strategy

- use foreign keys for structural relationships
- use check constraints for domain-specific values
- use unique constraints to preserve business identity semantics
- use soft-delete semantics via deleted_at rather than destructive delete

## 19. Soft Delete Strategy in Physical Terms

Soft delete should be implemented with a nullable deleted_at column on all major business tables.

### 19.1 Strategy

- default state: deleted_at is NULL
- logical deletion: set deleted_at to the current time
- exclude deleted rows from normal operational queries by default
- retain rows for audit, reporting, and lineage purposes

### 19.2 Tables That Should Support Soft Delete

- registry_identity
- registry_identity_attribute
- registry_identifier
- verification_case
- identity_evidence
- duplicate_case
- merge_case
- public_profile
- registry_authority
- authority_assignment
- registry_snapshot
- provenance_record

## 20. Audit Strategy in Physical Terms

The physical model provides explicit audit tables and immutable semantics for lineage and governance history.

### 20.1 Audit Tables

- registry_status_history for state transitions
- registry_change_record for state changes and corrections
- provenance_record for source, trust, and lineage metadata
- registry_snapshot for point-in-time state capture

### 20.2 Audit Principles

- preserve historical state instead of overwriting it
- keep audit rows append-oriented and partitioned by time
- record attribution through actor IDs or source metadata
- allow compliance queries without touching the current state tables

## 21. Summary

This PostgreSQL physical data model provides a robust enterprise foundation for the Global Registry Foundation. It translates the approved logical model into a normalized, policy-aware, audit-friendly, and query-optimized database architecture.

The design emphasizes:

- canonical identity management
- strong integrity and business-rule enforcement
- auditability and provenance
- public-safe lookup and resolution
- future extensibility by child registries
- PostgreSQL-native implementation patterns compatible with Supabase PostgreSQL

It remains deliberately architecture-oriented and does not cross into application implementation details.
